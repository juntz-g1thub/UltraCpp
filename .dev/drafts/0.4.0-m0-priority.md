## §1 背景

M0 计划本意是「无新功能」端到端验证：跑 47 个 .uc 程序（覆盖 0.3.0 spec §2-§5 的基础语法），全部应该 PASS，因为这些语法点不需要任何借用检查语义就能工作。**但当前基线 1/48 通过**（仅 `m0_01_minimal_main`）。

错位的根本原因：src-c/ 当前**只是 Partial 实现**，缺失 spec §2-§5 的大量基础语法点（`const` 全局、`++/--`、`alloc/free`、`unique T`、`三元`、`结构体`、`数组`、`extern "C"`、`#include`、CJK 标识符……）。M0 不能"无新功能"通过，必须补全 src-c/ 的 parser/lexer/codegen 才能达到 48/48。

路线：以 baseline 测试当 TDD，按 P0→P3 优先级逐步修复 src-c/。每个 P 级修复完跑一次 baseline 看通过数变化，commit 单修复。

## §9 风险与回退

### P0 风险

- **最大风险**：m0_47 ++/-- 修复在 `parse_postfix` 加 match 循环，可能误把 `x.y` 后续的 `++` 错误吞掉；m0_48 三元 `?:` AST 节点需新增 `UC_EXPR_TERNARY`，与 codegen 同步。
- **回退方案**：
  - 每个 P0 测试独立 commit；如 m0_47 引入回归，`git revert` 单 commit
  - 优先用最小改动策略（仅在 parse_postfix 末尾加 INC/DEC match，不改 call/field 分支）
  - 单元测试（`make -C src-c test` 505/505）必须保持全绿

### P1 风险

- **最大风险**：
  - m0_50 CJK 需要 UTF-8 解码 + LLVM 标识符映射；LLVM 标识符默认 ASCII，破坏 ABI
  - m0_09/m0_12/m0_15 控制流 codegen 涉及 phi 节点 / loop scope 状态机，bug 易扩散
- **回退方案**：
  - m0_50 可降级为 PARSE-ONLY（只验证 token 能识别，codegen 可 fallback 到 ASCII 哈希）
  - 控制流 codegen bug 一旦发现，按"最小修复"原则：先让单测试通过（如 m0_09），不要尝试一次性修复所有控制流
  - 如严重回归，回退到上一个 commit + 重做该测试

### P2 风险

- **最大风险**：
  - m0_44 多文件 module 系统涉及跨文件 symbol table，单文件内 symbol 表需先稳定
  - m0_41 extern "C" 涉及跨语言 ABI，破坏后难以调试
- **回退方案**：
  - m0_44 模块系统可暂时**跳过**（在 test-outline.md 中标记为「待补」），不影响其他测试
  - m0_41 extern "C" 失败可降级为 PARSE-ONLY
  - 数组/struct 类型扩展必须有 C 单元测试覆盖（避免 codegen 类型大小计算 bug）

### P3 风险

- **最大风险**：
  - 运行时失败定位难（IR 看不出问题，需 gdb + lldb）
  - 退出码非零 ≠ 程序错，可能只是 main 没正确返回（m0_02 大概率是这种情况）
- **回退方案**：
  - 每个 P3 测试单独建临时目录：`mktemp -d`，避免污染其他测试
  - 如无法修复某测试，记录到 `.dev/drafts/0.4.0-known-failures.md` 并标记为「接受遗留」
  - 不允许为了 P3 通过而**修改 .uc 测试期望**——这是测试驱动修复的底线

### 总体回退流程

如某 P 级整体未达目标（如 P0 完成后通过数 < 9）：

1. **停止当前 P 级修复**
2. **git log 找出引入回归的 commit**
3. **回退到回归前状态**
4. **重新评估**：是测试错（改 .uc）、还是 src-c 错（继续修）、还是根因归类错（调整 P 级）
5. **更新本计划 §3-§6**：把无法修复的测试移到 P3 或标记为「待重分类」
