## §1 背景

M0 计划本意是「无新功能」端到端验证：跑 47 个 .uc 程序（覆盖 0.3.0 spec §2-§5 的基础语法），全部应该 PASS，因为这些语法点不需要任何借用检查语义就能工作。**但当前基线 1/48 通过**（仅 `m0_01_minimal_main`）。

错位的根本原因：src-c/ 当前**只是 Partial 实现**，缺失 spec §2-§5 的大量基础语法点（`const` 全局、`++/--`、`alloc/free`、`unique T`、`三元`、`结构体`、`数组`、`extern "C"`、`#include`、CJK 标识符……）。M0 不能"无新功能"通过，必须补全 src-c/ 的 parser/lexer/codegen 才能达到 48/48。

路线：以 baseline 测试当 TDD，按 P0→P3 优先级逐步修复 src-c/。每个 P 级修复完跑一次 baseline 看通过数变化，commit 单修复。

## §7 执行流程（TDD 循环）

```
for each priority level (P0, P1, P2, P3):
    for each test in level (sort by 编号 + 依赖拓扑):
        1. 最小修复（src-c/ + 必要时调整 .uc 测试文件——但本计划禁止改 .uc）
           仅当 .uc 测试本身有 bug 时才改（见 §9 回退）
        2. cd src-c && make              # 重建编译器
        3. bash test/e2e/run_baseline.sh # 跑基线
        4. 确认新通过数 >= 预期 + 不破坏 m0_01
        5. git commit (单测试或单聚类)
           commit message 模板：
           "M0 P{0,1,2,3}: fix {test_id} ({brief})
            - {修复点}
            - baseline: {old_pass}/48 → {new_pass}/48
            Refs: docs/test-outline.md §3.{section}"
        6. 报告进度到 §8 表
```

**关键约束**：
- 每个 P 级内部按编号排序，但**有依赖的优先**（m0_22 必须在 m0_45 之前，m0_09 必须在 m0_10/m0_11 之前，m0_12/m0_13 必须在 m0_14/m0_15 之前，m0_26 必须在 m0_27/m0_28 之前，m0_32 必须在 m0_33 之前，m0_16 必须在 m0_18/m0_20 之前，m0_23 必须在 m0_24 之前，m0_29 必须在 m0_30 之前）

## §9 风险与回退

### P0 风险

- **最大风险**：m0_47 ++/-- 修复在 `parse_postfix` 加 match 循环，可能误把 `x.y` 后续的 `++` 错误吞掉；m0_48 三元 `?:` AST 节点需新增 `UC_EXPR_TERNARY`，与 codegen 同步。
- **P0-3 修复实际揭露 5 层 bug**（2026-08-12）：
  1. `parse_postfix` 未消费 `UC_TOK_OP_INC/DEC`（m0_47 直接 fix，commit `cb07848`）
  2. `parse_expression` 优先级链缺 ternary level（m0_48 直接 fix，commit `70b8845`）
  3. **codegen label 引用**：`emit` label-ref format string 在 8 处写了 `%%`（应写 `%`），commit `cf51f6f` 把所有 `%s`/`%d`/label 格式串中的 `%%` 全部改回 `%`——这是所有 br/jump 指令 emit 的系统性问题
  4. **codegen `emit_label`**：emit label 名字时又叠加一层 `%` 前缀，与 fix #3 形成双重 `%`；commit `f1f4214` 在 `emit_label` 处 strip 前导 `%`
  5. **`UC_STMT_IF` 结构**：原 emit 仅 then/else 两 label，缺 end label；phi 节点收敛不到统一 exit，control flow 必错——commit `3abe96b` 把 `UC_STMT_IF` 重构为 then/else/end 三 label + phi 在 end 处收敛
- 这 5 层 bug 修复**同时**让 m0_09 (if/else)、m0_10 (else if 链)、m0_11 (嵌套 if) 等 control flow 测试水落石出 PASS（即从 §8 表外 bump 到 PASS 但还没列入表）。属于 P1-2 范畴（control flow 三件套）的提前产出。
- safe-bash 当前状态：**resolved**（whitelist 已允许 `bash`/`make`/`git`/`grep`/`cat`/`find`/`cp`/`build`/`uc_lexer`/`run_baseline.sh` 直跑），不再是 P0-3 完成的阻塞。P0-2 期间 safe-bash 是 barrier；P0-3 期间已解决。
- **回退方案**：
  - 每个 P0 测试独立 commit；如 m0_47 引入回归，`git revert` 单 commit
  - 优先用最小改动策略（仅在 parse_postfix 末尾加 INC/DEC match，不改 call/field 分支）
  - 单元测试（`make -C src-c test` 505/505）必须保持全绿

- **新增已知缺口（2026-08-12，P0-2 完成时发现；2026-08-12 baseline run 复核）**：m0_34 / m0_36 **still FAIL**（runner 报 `compile_failed`，实际是 codegen `*p = X` deref-assign 在 store 指令处把 `ptr` 当 `i32` 处理——i32 vs ptr 类型错；pre-existing；详见 §8.1 codegen 桶）。这是 P3-5 范畴（m0_29 / m0_30 pointer runtime）的 known issue，不影响 parser / codegen 层验收；待 P3-5 修复 pointer runtime 时回看 m0_34 / m0_36 的 e2e 全跑通路径。

  - 每个 P3 测试单独建临时目录：`mktemp -d`，避免污染其他测试
  - 如无法修复某测试，记录到 `.dev/drafts/0.4.0-known-failures.md` 并标记为「接受遗留」
  - 不允许为了 P3 通过而**修改 .uc 测试期望**——这是测试驱动修复的底线

### 总体回退流程

如某 P 级整体未达目标（如 P0 完成后通过数 < 9）：

1. **停止当前 P 级修复**
2. **git log 找出引入回归的 commit**
3. **回退到回归前状态**
4. **重新评估**：是测试错（改 .uc）、还是 src-c 错（继续修）、还是根因归类错（调整 P 级）
5. **更新本计划 §3-§6**：把无法修复的测试移到 P3 或标记为「待重分类」
