## 1. Scope and method

This is a **static gap analysis** of what the UltraCPP 0.1 language specification and developer handbook define for ownership/borrowing, versus what the two compiler implementations actually do today. It is **not** a behavioral test suite, **not** a benchmark, and **not** an implementation plan.

What was checked:

- User-facing spec: `docs/UltraCPP-v0.1.0-spec-en.md` and `docs/UltraCPP-v0.1.0-spec-zh-CN.md` (sections 1.3, 2.2–3.3, 4.6, 4.8, 5.9, 6.3, 7, 10.3, 12.1, 12.2).
- Internal design doc: `.dev/plans/0.1.0-devhandbook.md` (sections 4.4–4.8, 5, 10.2, 12.2, 12.4).
- C host compiler: `src-c/src/{main,lexer,parser,codegen,ast,token,error}.c`, `src-c/include/{uc_token,uc_parser,uc_codegen,uc_error,uc_lexer,uc_ast}.h`, `src-c/src/parser.c`, `src-c/tests/test_*.c`.
- Rust reference: `src/main.rs`, `src/frontend/{mod,lexer,token,parser,ast}.rs`, `src/semantic/{mod,checker,ownership,resolver}.rs`, `src/codegen/*`.
- Test programs: `test/test_t{1,2,3}/main.upp`, `test/test_hello_world/main.upp`, `test/test_io/main.upp`, `test/test_include/main.upp`, `test/test_simple.uc`, `lib/{io,math}.uc`.

Three readings of "implementation":

1. **Compiler-level semantic enforcement** — static rejection of violating programs at compile time. This is what the spec "compile-time memory safety" goal demands.
2. **Runtime checks** — instrumentation injected at codegen (e.g. null-page traps, refcount). Not in scope for the spec but noted where present.
3. **No support** — the feature is neither in the parser nor in the type system.

A feature is "Implemented" only if (1) holds. Parsing-only support (e.g. the lexer recognizes `unique` as a keyword but no check is performed) is **Partial** at best and **Not implemented** at worst.

Caveats and missing material:

- The `Owned<T>` / `Ref<T>` / `RefMut<T>` type kinds described in the devhandbook (§4.1) do not appear in the spec's EBNF (§12.1) or in either compiler's `Type` enum. The devhandbook describes a Rust-like internal type representation; the spec and the implemented languages do not.
- The devhandbook's `Borrow` struct (§4.4) and `OwnershipError` enum (§4.6) exist only as pseudocode in that document. There is no header / module file in either compiler that defines these.
- The `&mut` token is missing from both lexers. See §7.

## 2. Spec summary — ownership/borrow rules

The following rules are derived from the spec (`docs/UltraCPP-v0.1.0-spec-en.md`, abbreviated `EN`), the Chinese spec (`docs/UltraCPP-v0.1.0-spec-zh-CN.md`, abbreviated `ZH`), and the devhandbook (`DH`). Quotes are verbatim.

| ID | Rule statement | Source quote | Error kinds |
|---|---|---|---|
| R-OWN-1 | **Non-copyable pointer types.** All `T*` are non-copyable by default; assignment transfers ownership. | "All pointers are non-copyable by default; assignment transfers ownership." (`EN §7.1`, `ZH §7.1`) | Use-after-move |
| R-OWN-2 | **Explicit `move(p)`** — source becomes null. | "move() explicitly transfers ownership; source pointer becomes null." (`EN §7.4`) | Use-after-move |
| R-OWN-3 | **Explicit `clone(p)`** — both pointers independent. | "clone() copies the pointer; both have independent ownership." (`EN §7.5`) | Double-free (if misuse) |
| R-OWN-4 | **`alloc(T)` / `free(p)`** without grammar enforcement. | "alloc(T) … free(ptr)" (`EN §1.3`); "free(p) Free memory" (`EN §7.3`) | Double-free, use-after-free |
| R-OWN-5 | **`unique T` is the explicit exclusive-ownership pointer**; same default; can be omitted. | "unique: Explicit exclusive ownership pointer (same as default, can be omitted)" (`EN §3.7`); "unique T" (`EN §12.1`) | Use-after-move |
| R-OWN-6 | **Function parameters own the argument** (pass-by-value → ownership transfer). | "Parameters are copied to function parameters" + "Modifying parameters doesn't affect arguments" (`EN §6.3`); pointer-arg move semantics implied by `EN §7.1`. | Use-after-move |
| R-OWN-7 | **Use-after-move is rejected.** | DH §4.5 "移动转移: 移动使源变量失效" + DH §4.6 `UseAfterMove`; DH §12.2 `ownership_checker_check_use` returns `OWNERSHIP_ERROR_USE_AFTER_MOVE`. | UseAfterMove |
| R-OWN-8 | **Use-after-drop is rejected.** | DH §4.6 `UseAfterDrop`; DH §12.2 `ownership_checker_check_use` returns `OWNERSHIP_ERROR_USE_AFTER_DROP`. | UseAfterDrop |
| R-OWN-9 | **Borrow conflict** — many `&` OK, but not with `&mut`; `&mut` cannot coexist with anything. | "允许多个不可变借用; 允许一个可变借用; 不可变和可变借用不能同时存在" (`DH §4.5`); DH §4.7 `check_borrow_conflict`. | BorrowConflict |
| R-OWN-10 | **Dangling reference** (escape of a pointer/reference beyond its owner). | DH §4.6 `DanglingReference`; DH §12.4 lifetime inference. | DanglingReference |
| R-OWN-11 | **`unsafe { ... }` block** suppresses ownership inside, but the keyword exists in the spec body. | "unsafe { // FFI calls and raw pointer operations }" (`EN §10.3`); "unsafe" listed as keyword (`EN §2.2`). | (suppresses enforcement) |
| R-OWN-12 | **`null` constant** — pointer may be null; comparison `p == null` is OK; deref of null is UB. | "int* p = null; if (p == null) {" (`EN §7.6`). | (runtime, not enforced statically in spec) |

Notes on what is *not* in the spec:

- The spec's EBNF (`EN §12.1`) defines `unary_expression` as `'+' | '-' | '!' | '~' | '*' | '&'`. There is **no `&mut` token or production**. The devhandbook (§4) describes `&mut` and borrow conflict in detail, but the user-facing spec only defines bare `&` as a unary operator. This is a spec inconsistency: the devhandbook's borrow checker is unreachable from the spec's grammar as written.
- The spec lists `move` and `clone` in the operator precedence table (`EN §4.1` level 15) but their EBNF placement (`unary_expression`) puts them after `*` and `&`, with the prefix-call form `move(expr)` and `clone(expr)` (per `EN §12.1` `unary_expression`).
- The spec does **not** define separate `Ref<T>` / `RefMut<T>` types (which the devhandbook's `Type` enum declares). The spec only defines `T*`, `T* const`, `const T*`, `T&`, `T(*)(U)`, `T[n]`, `struct` (§3.2, §3.3, §3.4, §3.5).

## 4. Pipeline / module map

### C host (`src-c/src/main.c`)

The CLI dispatches to one of four modes (`--tokens`, `--ast`, `--emit-ll`, `--build`). The only code path that goes beyond tokens is:

```
slurp_file
  → uc_lexer_init           (src/lexer.c)
  → uc_parser_parse         (src/parser.c)
  → uc_codegen_generate     (src/codegen.c)
  → write / llc / gcc       (no compiler-internal pipeline)
```

Evidence: `src-c/src/main.c:174-261` (`run_dump_ast`, `run_emit_ll`, `run_build`). **There is no ownership / semantic pass between parser and codegen.** The `scan_imports` helper (`src-c/src/main.c:107-150`) is a regex-style scan over `buf` for `#import` lines and only feeds the codegen's import list — it does not enforce or check.

### Rust reference (`src/main.rs`)

```
fs::read_to_string
  → preprocess                (src/preprocessor.rs)
  → Lexer::new + Parser::new  (src/frontend/{lexer,parser}.rs)
  → CodeGenerator::generate   (src/codegen/generator.rs)
  → fs::write / llc / gcc
```

Evidence: `src/main.rs:34-82` (`main`); `src/frontend/mod.rs:42-49` (`compile`) returns immediately after `parser.parse()?` — **`semantic::checker`, `semantic::ownership`, `semantic::resolver` are all unreachable from `compile()`**. Confirmed by `grep -rn "OwnershipChecker\|TypeChecker\|Resolver::new" src/`: 3 matches, all in `src/semantic/*.rs` itself, never called from `src/main.rs` or `src/frontend/mod.rs`.

The `OwnershipChecker` struct exists (`src/semantic/ownership.rs:7`) but its `check_expr` is a one-liner stub returning `Ok(())` (`src/semantic/ownership.rs:17-20`). The file header says: *"For strict compile-time checking, this would be expanded to track pointer validity statically."*

### Comparison

| Stage | C host | Rust reference |
|---|---|---|
| Lexer | `src/lexer.c` | `src/frontend/lexer.rs` |
| Parser | `src/parser.c` | `src/frontend/parser.rs` |
| Type checker | ❌ none | ⚠️ `src/semantic/checker.rs` exists, never called |
| Ownership checker | ❌ none | ⚠️ `src/semantic/ownership.rs` exists, never called, stub |
| Resolver | ❌ none | ⚠️ `src/semantic/resolver.rs` exists, never called |
| Codegen | `src/codegen.c` (LLVM IR) | `src/codegen/generator.rs` (LLVM IR) |

The two compilers are at structurally the same point: a parser that produces an AST, then a direct path to LLVM IR. The Rust reference has the kernel of a semantic layer but it is dead code.

## 7. Open questions raised by the audit

These are decisions that the spec and/or devhandbook do not make explicit, and which must be resolved before any verification scheme can be built. They are surfaced here, not answered.

1. **Is `unique T` a generic type or a hard-coded `unique int`?** Both parsers hard-code it to `Pointer(Int)`. The spec uses `unique` like any other type (`EN §3.7`, `EN §12.1` `unary_expression` shows `*`/`&` types over arbitrary types). Going by the spec, both parsers are buggy.
> **Outcome (v0.3.0)**: Resolved: yes, `unique T` is equivalent to `T*` (Q1=C).
2. **Does `&` mean "address-of" or "immutable borrow"?** Both parsers thunk it to `UC_UN_ADDR_OF` / `UnaryOp::AddrOf`. The spec table (`EN §2.6`) lists `&` as "Bitwise AND/address-of" — no borrow meaning. The devhandbook §4.5–4.7 describes borrow semantics. Asked differently: should `int* p = &x;` be a move (no, `p` is fresh), a borrow (no, `p` is fresh), or just an address (today)?
> **Outcome (v0.3.0)**: SUPERSEDED — 0.3.0 dropped the 'immutable borrow' framing; `T&` is a shared-writable reference requiring `mod()`.
3. **Is `&mut` part of the language at all?** Not in the spec's EBNF (§12.1) or operator table (§4.1). Yes in the devhandbook (§4.5). The devhandbook's compiler architecture diagram (§1.1) lists "ownership verification" as a stage. If `&mut` is in, the spec must add it; if out, the devhandbook must remove it.
> **Outcome (v0.3.0)**: SUPERSEDED — `T&mut` was removed in 0.3.0 (see §10-6). Exclusivity now via `#modlaw exclusive` + `mod()`.
4. **Is `move(p)` syntactic sugar for `p = null; p_new = p;` or a real primitive?** Spec §7.4 says it transfers ownership and nulls the source. Parsers only produce an AST node. The devhandbook §4.8 talks about `record_move` but does not say what `move` produces at runtime.
> **Outcome (v0.3.0)**: Resolved: real primitive, not sugar (D-4).
5. **What does the spec mean by "non-copyable" `T*`?** Is assignment a move (source nulled) or a copy (which is forbidden)? §7.1 says "p1 becomes null". Does the compiler emit IR that nulls `p1`, or does it rely on C's natural pointer copy? Both impls today emit the latter.
> **Outcome (v0.3.0)**: SUPERSEDED — 0.3.0 Q4 changed assignment semantics: `dst = src` gives `dst` implicit modification rights; **source is NOT nulled**. Explicit `move(src)` is required for ownership transfer.
6. **Should `alloc` / `free` be grammar-enforced (every `alloc` must have a matching `free`)?** Spec only says they exist. Devhandbook §4.6 does not list a `MissingFree` or `DoubleFree` error kind. Today's behavior: no check at all.
> **Outcome (v0.3.0)**: Resolved: not enforced in 0.3.0; alloc/free pairing is programmer responsibility (Q6=C).
7. **What is a "dangling reference"** in a language that has no first-class reference type? Spec §3.3 has `T&` but never uses it in examples that would dangle. Devhandbook §4.6 mentions `DanglingReference { owner_location }` but does not define what triggers it.
> **Outcome (v0.3.0)**: Resolved: defined in 0.3.0 §7.9 — owner out of scope, or reference returned to local.
8. **Is the `semantic/` module in `src/` intended to be revived, or is the C host the production compiler going forward?** Both compilers are at the same level today, but only the Rust reference has a (dead) semantic module. The worktree is named `borrow-check-verification` — the audit does not know whether the goal is to (a) light up the dead Rust module, (b) port the devhandbook's pseudocode to C, or (c) do both.
> **Outcome (v0.3.0)**: Resolved: C host is mainline (D-8); Rust remains reference, gradually deprecated.

## 8. Suggested next actions

In increasing order of commitment. Each item says what file/area, estimated size, and what blocks it.

1. **Pick a target language for the spec/devhandbook inconsistency.** Size: S. Blocked by: question §7-3 + §7-8. Concretely: decide whether `&mut` is in the language, decide whether `unique T` is generic, then patch either `docs/UltraCPP-v0.1.0-spec-en.md §3.7 + §12.1` or `.dev/plans/0.1.0-devhandbook.md §4.5` to match. This is prerequisite to writing any check.
2. **Add `&mut` to one lexer first (recommended: Rust, since `src/frontend/lexer.rs` already has the `&` branch to extend).** Size: S. Blocked by: question §7-3. Adding `KwMut` + a peek-and-advance branch in `scan_identifier` and in `&` arm of `next_token` (around line 116) gets the grammar in place. ## §10-7 0.3.0 outcome reconciliation (2026-08-07)

The following 0.3.0 spec changes are NOT covered by §7 / §9 / §10-1..10-6 (which predated the two-permission-model turn). They are recorded here for completeness.

### Rule 22 — 两条权限彻底拆分 (NEW in 0.3.0)

Ownership and modification rights are independent dimensions.

- **所有权**: 决定谁 delete/free；唯一 owner；可显式转移；不可复制
- **修改权**: 决定谁能改值；可多可少可独占；由用户配置

→ v0.3.0 §1.2 设计原则 + §7.1 所有权语义。

### Rule 23 — `#modlaw` 指令 (NEW in 0.3.0)

Modification rights controlled by preprocessor directive. Syntax:
```
#modlaw <perm> <scope>
```

6 种合法组合：`none|exclusive|shared` × `global|module`。

→ v0.3.0 §9.9 #modlaw 指令。

### Rule 24 — `mod()` / `unmod()` 表达式 (NEW in 0.3.0)

```cpp
mod(ref_expr)    // 申请修改权（按 #modlaw 决定行为）
unmod(ref_expr)  // 显式释放（一般靠作用域自动）
```

→ v0.3.0 §4.9 / §4.10。

### Q4 — 赋值为隐式 mod() (CHANGED in 0.3.0)

- 旧 (D-5 / 0.2.0): `p1 = p2` → 源变 null，p1 接管所有权
- 新 (Q4 / 0.3.0): `p1 = p2` → 隐式 mod(p1)，源仍 own，p1 仅获得修改权

→ v0.3.0 §7.1.1 赋值的 move 规则。

### Q6 — const T* / T* const 自定义语义 (NEW in 0.3.0)

与 C++ 反向：
- `const T*` = 指针本身锁定 + 生命周期安全 + 不可写
- `T* const` = 数据只读视图

特殊规则：owning heap 变量**不能**造只读指针（owning 可能被 move/free）。

→ v0.3.0 §3.8 + §7.10 / §7.11。

### Rule 25 — 跨线程 `shared` 标注强制 (NEW in 0.3.0)

`shared` 标注**强制**：跨线程访问的变量必须标注，否则编译错。编译器自动生成 mutex + 程序员可选显式 `mutex<T>`（避免双重加锁）。

→ v0.3.0 §13.1 共享变量。

### Rule 26 — 跨线程所有权 (NEW in 0.3.0)

```cpp
move_to_thread(p, tid)            // 显式移交
spawn_thread_with(tid, p)         // spawn 时隐式 move
```

→ v0.3.0 §13.2。

### Rule 27 — `__thread` 线程局部存储 (NEW in 0.3.0)

```cpp
__thread int local = 42;  // 每线程独立
```

→ v0.3.0 §13.5。

### Rule 28 — 多线程内存布局 (NEW in 0.3.0)

栈 = thread-local；堆 = shared；全局/静态 = shared；TLS = thread-local。跨线程传引用只允许 heap / global / TLS，不允许 stack。

→ v0.3.0 §13.4。

### 删除：T&mut (REVERSAL recorded in §10-6)

`T&mut` 在 0.3.0 中已删除。独占性不再由类型区分，而由 `#modlaw exclusive` + `mod()` 实现。

→ v0.3.0 §3.3 + §7.8。
