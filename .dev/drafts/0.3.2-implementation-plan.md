## 3. 问题描述

### 3.1 m0_42 现状 (`malloc(8)` 类型错)

**测试源** (`test/programs/baseline/m0_42_unsafe_block.uc`):

```cpp
unsafe {
    int* view = (int*)malloc(8);   // ❌ (int*) C-style cast 0.3.1 无, parser 拒
    *view = payload;               // ❌ deref-assign LHS (S2 部分修, 但需 cast)
}
```

**当前错误**:
1. `(int*)malloc(8)` — 0.3.1 parser **不识别 C-style cast**, 直接 `compile_failed`
2. `*view = payload` — S2 (0.3.1) 修了 LHS lvalue 路径, 但前提是 `view` 类型正确

**修复路径**:
- **S4** (§4.8.1): parser 加 `(T)expr` cast 语法
- **S5** (§11.0): codegen 知道 `malloc` 返回 `void*` (从签名表), cast 到 `int*` 后 `view` 类型 = `int*`
- **Bug C1** (UC_EXPR_CALL): `malloc(8)` 调用后正确设置 `last_expr_type` = `void*` (i8*)
- **S2 (0.3.1) 已修**: `*view = payload` LHS 走 lvalue 路径 emit gep, store `payload`

**修复后**:
- `(int*)malloc(8)` → codegen: `bitcast i8* %retval to i32*`
- `*view = payload` → codegen: `getelementptr i32, i32* %view, i64 0` + `store i32 %payload, i32* %gep`
- m0_42 PASS

### 3.2 m0_41 现状 (abs_int 链接错)

**测试源** (`test/programs/baseline/m0_41_extern_c.uc`):

```cpp
extern "C" {
    int abs_int(int x);   // 无 body 的 extern 声明
}

int main() {
    int v = abs_int(-5);
    return v;             // 返回 5
}
```

**当前错误**:
1. `abs_int` 是 extern 声明, 无 body
2. codegen 不知道 `abs_int` 的返回类型 (没有 builtin 签名表), **硬编码 i32**
3. 实际链接时 `abs_int` 是 libc 的 `abs()`, 签名是 `int abs(int)`, 名字 `abs_int` 不存在 → **link_failed**

**修复路径**:
- **S5** (§11.0 builtin 签名表): 把 `abs_int(int) → int` 收录到 §11.0 表
- **Bug C2** (UC_EXPR_CALL 硬编码 i32): codegen 查表得 `abs_int` 返回 `i32` → 一致
- codegen emit `declare i32 @abs_int(i32)` (不 emit body), link 时由 libc 提供 (但 `abs_int` ≠ libc `abs`)

**实际难点**:
- 严格说 `abs_int` 是 m0_41 测试**人造**的 extern 名字, libc 没这个符号
- 修法选择:
  - **方案 A**: 收录 `abs_int` 到 §11.0 builtin, codegen 直接 emit `@builtin_abs_int` (内置实现)
  - **方案 B**: 收录 `abs_int` 到 §11.0 builtin, codegen 仍 emit `declare i32 @abs_int(i32)`, 让 m0_41 改成调用 builtin `abs()`
- **0.3.2 选择**: 方案 A (更直接, m0_41 测试源不改)

**修复后**:
- m0_41 测试源**不变**
- codegen: `abs_int(-5)` → `call i32 @builtin_abs_int(i32 -5)` (builtin_sigs 提供类型, emit builtin 实现)
- m0_41 PASS

### 3.3 Bug C1 + C2 + C3 描述

#### Bug C1: `UC_EXPR_CALL` 不设 `last_expr_type`

**位置**: `src-c/src/codegen.c` 的 `UC_EXPR_CALL` case (~行 800 附近)。

**当前代码** (伪代码):
```c
case UC_EXPR_CALL:
    // emit args
    // emit call instruction
    const char* expr_type = g->last_expr_type
                                    ? g->last_expr_type : "i32";  // ← Bug C2 硬编码
    // 没有"设置 last_expr_type = 函数返回类型"的代码
    break;
```

**问题**: 调用 `factorial(5)` 后, `last_expr_type` 仍是上一次的值 (e.g. `i32` from 字面量)。后续 `int x = factorial(5);` 类型检查时, 拿到的不是 `factorial` 的真实返回类型。

**修复**: 在 `UC_EXPR_CALL` case 末尾加:
```c
free(g->last_expr_type);
g->last_expr_type = cgen_strdup(ret_type);  // ret_type 来自 §11.0 表或函数定义
```

**预估**: 1-2 LOC。

#### Bug C2: `UC_EXPR_CALL` 返回类型硬编码 i32

**位置**: `src-c/src/codegen.c` 的 `UC_EXPR_CALL` case (同 C1)。

**当前代码**: 见 C1 的 `expr_type = g->last_expr_type ? g->last_expr_type : "i32";`

**问题**: 当 `last_expr_type` 未设置时, fallback 到 `"i32"`, 但 `malloc` 返回 `i8*` (void*), `strlen` 返回 `i32`, `is_null` 返回 `i1`。硬编码 i32 导致 m0_29 / m0_31 等**已经 PASS** (侥幸), 但 m0_42 (`malloc(8)` 后 `*view = payload`) 类型错。

**修复**: 由 §11.0 builtin 签名表提供正确返回类型 (S5 同步修)。`UC_EXPR_CALL` 查表:
```c
const builtin_sig_t* sig = lookup_builtin(fn_name);
if (sig) {
    ret_type = sig->ret_type;  // e.g. malloc → "i8*", strlen → "i32"
} else {
    // 用户/extern 函数, 从符号表取
    ret_type = lookup_user_func_ret_type(fn_name);
}
```

**预估**: 5-10 LOC。

#### Bug C3: m0_42 deref-assign LHS (部分由 S2 解决)

**位置**: `src-c/src/codegen.c` 的 `UC_EXPR_ASSIGN` 处理 LHS 路径。

**当前状态** (S2 0.3.1 部分修):
- `gen_expr` 加 `int in_lvalue_ctx` 参数
- `UC_EXPR_ASSIGN.target` 调用时传 `in_lvalue_ctx=1`
- `UC_UN_DEREF` (`*p`) 在 `in_lvalue_ctx` 时 emit gep (取地址), 否则 emit load

**S2 局限**:
- S2 修的前提是 `view` 类型正确 (`int*`)
- 0.3.1 当前 `view` 类型来自 `(int*)malloc(8)`, 但 **0.3.1 无 C-style cast**, `view` 类型推断不出来
- 结果 S2 修了 lvalue 路径, 但 m0_42 仍因 cast 缺失 compile_failed

**0.3.2 完整修**:
- S4 (C-style cast) + S5 (返回类型) 共同让 `view` 类型 = `int*`
- S2 (0.3.1) lvalue 路径正常工作 → m0_42 PASS

**预估**: 0 LOC (S2 + S4 + S5 协同, 无新代码)

### 3.4 强绑定关系

| 绑定 | 原因 |
|------|------|
| **S4 + S5 强绑定** | cast 需知道 cast 到的类型 (§3 类型系统), S5 提供 builtin 函数的返回类型 |
| **S5 + Bug C2** | codegen 查 §11.0 表得返回类型, 取代硬编码 i32 |
| **Bug C1 + S5** | UC_EXPR_CALL 设置 `last_expr_type` 时, 取值来自 §11.0 表 |
| **S2 + S4 + S5** | m0_42 完整修需要三者协同 (S2 lvalue 路径 + S4 cast 语法 + S5 返回类型) |

**总判断**: 0.3.2 是**强耦合**修复集, 必须**全部完成**才能让 m0_42 + m0_41 翻 PASS。

## 4. 现有 spec 章节交互分析

### 4.1 §4.8 + §6.2 + §11 + S2 已有的 lvalue 概念

**§4.8 当前** (4 行):
```
### 4.8 带括号表达式
(expr)  // 括号中的任意表达式
```

**§4.8.1 (0.3.2 新增)** C-style cast 与 §4.8 现有"括号表达式"是**特殊化关系**:
- `(`*expr*`)` 是括号表达式 (§4.8)
- `(`*type*`)` *expr* 是 C-style cast (§4.8.1)
- 区分:`(` 后跟**类型名** vs **表达式** — parser 区分

**§6.2 当前** (5 行) 与 **§6.2.1 (0.3.2 新增)**:
- §6.2 是**调用语法**
- §6.2.1 是**返回类型规则**
- §6.2.1 不破 §6.2, 是 §6.2 的"返回类型"维度的补充

**§11 当前** (散落 6 子节) 与 **§11.0 (0.3.2 新增)**:
- §11.x 是**详细说明**
- §11.0 是**签名总表**
- §11.0 是 §11 的"目录 + 索引", 各 §11.x 加双向引用

**S2 lvalue 概念** (§4.13, 0.3.1) 与 §4.8.1 cast:
- cast 源 `expr` 是 rvalue (§4.13.2 表)
- cast 目标 `T` 决定结果类型
- cast 结果 `T` 类型值本身在赋值/子表达式上下文是 rvalue (新值)

**结论**: **§4.8 + §6.2 + §11 + S2 与 0.3.2 新增章节无冲突**, S4/S5 是补充而非替代。

### 4.2 与 §4.9 mod / §4.10 unmod / §7.1 所有权 的关系

**§4.9 mod()**:
- 操作数是 `T&` lvalue
- 与 0.3.2 cast 关系: cast 不影响 `mod()` 操作数约束

**§4.10 unmod()**:
- 同 §4.9, 操作数是 `T&` lvalue
- 与 0.3.2 cast 关系: 同 §4.9

**§7.1 所有权 + 隐式 mod**:
- `p1 = p2` (T*) 自动生成 `mod(p1)`
- 隐式 mod 的目标 `p1` 是 lvalue (§4.13.2)
- 与 0.3.2 cast 关系: cast 后 `view = (int*)malloc(8)`, `view` 是 lvalue (赋值 LHS), 隐式 mod 适用

**结论**: **与 §4.9 / §4.10 / §7.1 无冲突**, 0.3.2 cast 不破 mod / unmod / 所有权。

### 4.3 与 §4.6 赋值 的关系

**§4.6 当前** (0.3.1 修订):
- 11 个赋值 op, 统一加 "LHS 必须是 lvalue (见 §4.13.2)"
- LHS 是 lvalue, RHS 是 rvalue
- 隐式 mod 在 `=` 时 (T*)

**与 0.3.2 cast 关系**:
- cast 表达式 `T(expr)` 是 rvalue (新值), 可作 RHS
- cast 表达式**不**可作 LHS (rvalue)
- 赋值不变, 与 cast 解耦

**结论**: **与 §4.6 无冲突**, cast 不影响赋值语义。

### 4.4 综合: 5 个章节交互无冲突

| spec 章节 | 0.3.2 关系 | 净效果 |
|-----------|-----------|--------|
| §4.8 (括号) | 强化 (cast 是特殊化) | cast 加 §4.8.1 |
| §4.9 mod | 独立 (mod 操作数是 T&) | 无影响 |
| §4.10 unmod | 独立 | 无影响 |
| §4.6 赋值 (0.3.1) | 独立 | 无影响 |
| §6.2 函数调用 | 强化 (§6.2.1 是返回类型规则) | 0.3.2 加 §6.2.1 |
| §11 标准库 | 强化 (§11.0 是签名总表) | 0.3.2 加 §11.0 |
| §7.1 所有权 | 独立 | 无影响 |
| S2 §4.13 lvalue | 协同 (cast 源是 rvalue) | S2 已涵盖 |

**总判断**: **0.3.2 完全是 spec 概念强化 + bug fix**, 不破任何现有章节。
