## 2. 背景与触发 (Background and trigger)

0.3.2 codegen 阶段（commit `8cfc43a` + `2172fc6`）完成了 0.3.2 闭环，最终产出 **32/48 PASS**。该阶段在 `BUILTIN_SIGS[]` 中列出了 14 个候选函数（`src-c/src/codegen.c:19-25`），但其中**只有 4 个**（`alloc` / `move` / `clone` / `null`）有真正的 codegen 落地的 body；其余 10 个（`strlen` / `strcpy` / `strcmp` / `memcpy` / `memmove` / `memset` / `abs_int` / `free` / `mod` / `unmod` 等）只有签名、未实现 codegen 落地的 body——一旦用户调用就会**链接失败**。

这次 "32 PASS / 16 未完整覆盖" 的结果暴露出一个更深层的设计问题：**"builtin" 的边界到底在哪里？** 一个东西什么时候应该叫 "builtin"（编译器内建、语言原语）？什么时候应该叫 "library function"（标准库 / libuc）？这两者有什么区别？

之前 0.3.3 计划 A 给出了一个临时划分（**7 项**：alloc / move / clone / null / is_null / sizeof / alignof），但它没有正面回答这个根本问题。

今日用户明确澄清了：

> **UltraCPP 不应该使用 libc 作为 runtime。所有 stdlib（strlen / strcpy / printf / abs / ...）全部由 UltraCPP 自己实现。不转发 libc、不通过 `extern "C"` 接 libc。用 UltraCPP 语言本身写 runtime（自举）。**

这个澄清把 runtime 架构问题从 "0.3.3 的局部划分" 提升到了 "整个 0.3.x 阶段的战略决策"。本决策记录正式取代 0.3.3 计划 A 的临时划分，给出**最终、清晰、可执行的** runtime 策略。

## 3. 核心决策 (Core decisions)

### 3.1 UltraCPP 不使用 libc 作为 runtime

**已决定。**

- 所有 stdlib（`strlen` / `strcpy` / `printf` / `abs` / ...）全部由 UltraCPP 自己实现。
- 不转发 libc，不通过 `extern "C"` 接 libc。
- 用 UltraCPP 语言本身写 runtime（自举路径在 §9）。
- `extern "C"` 块仅用于**用户自己**声明外部 C 函数（例如调用系统库、遗留 C 代码），不用于 stdlib。

> 原则：UltraCPP 的 stdlib 是 first-class UltraCPP 公民，而不是 "外包给 libc"。

### 3.2 所有权/修改权相关函数全部为 builtin

**已决定。**

下列 6 个函数全部划为 **A 类 builtin**：

| 函数 | 语义 |
|---|---|
| `alloc(T)` | 分配 T 类型值的所有权 |
| `free(p)` | 释放 p 的所有权（p 之后不可访问）|
| `move(p)` | 转移 p 的所有权（p 之后不可访问，返回所有权）|
| `clone(s)` | 深拷贝 s，原 s 不变 |
| `mod(ref)` | 开启/进入对 `ref` 指向数据的可修改借权 |
| `unmod(ref)` | 结束/退出对 `ref` 指向数据的可修改借权 |

这与 0.3.3 计划 A 简化的 7 项不同——之前 `free` / `mod` / `unmod` 不在 BUILTIN_SIGS[]。但把它们降级为 FFI 或 intrinsic 会导致 borrow-checker 无法在所有 call site 强制跟踪所有权和修改权状态，因此**全部 6 项提升为 builtin**。

> 原则：**任何会让 borrow-checker 状态发生变化的函数，必须是 builtin**——它必须由 UltraCPP compiler 显式 emit IR marker，borrow-checker 才能可靠地追踪。

### 3.3 系统调用单独抽象为 `sys::` namespace

**已决定。**

- 跨平台统一命名：`sys::read` / `sys::write` / `sys::open` / `sys::close` / ...（详见 §6.2）。
- 不使用 `sys$` 前缀 hack（避免与用户符号冲突）。
- 模仿 glibc 模式：high-level wrapper + low-level `syscall()` + inline assembly（详见 §4.1 + §6）。
- UltraCPP 自己实现跨平台抽象，跨平台差异用 `@ifdef(TARGET_OS_*)` 区分（详见 §7）。

### 3.4 预编译宏采用 C 风格

**已决定。**

```c
@ifdef(TARGET_OS_LINUX)
    // Linux 实现
@end

@if defined(TARGET_OS_LINUX) && defined(TARGET_ARCH_X86_64)
    // x86_64 Linux 特定代码
@end
```

- 不采用 Rust 风格的 `#[cfg(target_os = "linux")]`。
- 理由：与 C 生态工具链兼容；与 `src-c/` 现有的 C 实现无缝；学习曲线友好。
- `@` 前缀避免与用户代码标识符冲突。

### 3.5 内联汇编采用 C 风格

**已决定。**

```c
asm {
    "syscall"
    : "=a"(result)               // 输出操作数
    : "0"(num), "D"(arg1)        // 输入操作数
    : "rcx", "r11", "cc", "memory"  // clobbers
}
```

- GCC 约束语法（`"r"` / `"a"` / `"D"` / `"=a"` / ...）。
- 不采用 Rust 风格 `asm!` 宏。
- 理由：LLVM 工具链直接理解；与 `src-c/` 当前 C 实现无缝；与 §3.4 预编译宏一致使用 C 生态约定。

## 4. 设计参照 (Design references)

### 4.1 C / glibc 模式

C / glibc 是 UltraCPP runtime 架构的主要参照系，因为它的工作方式久经考验。

**量级对比**：

| 类别 | 数量 |
|---|---|
| C 语言 builtins（`__builtin_*` 等）| ~370 个 token / ~30 个属性 |
| glibc runtime 函数（POSIX + GNU 扩展）| ~1,950 ~ 2,000 个函数 |
| **比例** | **glibc 是 C builtins 的 ~5.4 倍 surface area** |

**glibc 系统调用模型**（UltraCPP 的范本）：

```
用户代码
    read(fd, buf, n)
        ↓
glibc 高层 wrapper（posix/read.c）
    int read(int fd, void *buf, size_t nbytes) {
        return SYSCALL_CANCEL(read, fd, buf, nbytes);
    }
        ↓
glibc 低层 entry（sysdeps/unix/sysv/linux/x86_64/syscall.S）
    __syscall_cancel_read:
        movq $SYS_read, %rax     // 加载 syscall number
        syscall                  // 触发系统调用
        ...
        ↓
机器码
    syscall 指令
        ↓
Linux kernel
```

**glibc `read()` 的关键事实**：

- `read()` 是**运行时函数**（NOT a C builtin）；C 编译器不内置 `read`——它通过 libc 提供。
- glibc `syscall()` 通过**内联汇编**实现（`syscall.S`）。
- gcc 内联汇编约束语法：`"r"` (通用寄存器) / `"a"` (rax) / `"D"` (rdi) / `"S"` (rsi) / `"d"` (rdx) / `"c"` (rcx) / `"=a"` (输出) / `"memory"` (clobber 内存)。

UltraCPP 借鉴这一三段式架构（high-level wrapper + low-level entry + inline assembly），但用 UltraCPP 语言本身实现，而不是 C。

### 4.2 Rust 模式 (作为命名/组织参照)

Rust stdlib 设计对 UltraCPP 有借鉴价值（特别是 `std::sys` 模块化），但语法层不采用。

**Rust std::sys 模型**：

- Rust std 绝大部分**用 Rust 写**（few `extern`），是自举典范。
- 系统调用通过 `std::sys::pal::unix`（Linux + macOS）/ `std::sys::pal::windows` 等 PAL（Platform Abstraction Layer）模块。
- 跨平台条件编译：`#[cfg(target_os = "linux")]` / `#[cfg(all(target_os = "linux", target_arch = "x86_64"))]`。
- 内联汇编：`asm!("syscall", out("rax") result, in("rax") num, in("rdi") arg1)`。

**UltraCPP 借鉴 Rust 的「`std::sys` 模块化 + 自举 stdlib」理念**（命名、组织），但**保留 C 风格的预编译宏 + 内联汇编语法**（实现层）。

| 设计维度 | Rust | UltraCPP | 理由 |
|---|---|---|---|
| stdlib 实现语言 | Rust | UltraCPP | 自举 |
| 系统调用 namespace | `std::sys::pal` | `sys::` | UltraCPP 简化、显式 |
| 条件编译 | `#[cfg(...)]` | `@ifdef(...)` | C 风格 |
| 内联汇编 | `asm!` 宏 | `asm { ... }` 块 | C / GCC 风格 |
| 模块化 | `mod` 关键字 + 文件分块 | 文件直接 include + `@ifdef` | 简单 |

## 5. BUILTIN_SIGS[] 最终划分 (Final BUILTIN_SIGS[] partition)

### 5.1 BUILTIN_SIGS[] 最终表（6 项）

| 函数 | 类别 | 之前 | **现在** | codegen 处理 | runtime 提供方 |
|---|---|---|---|---|---|
| `alloc(T)` | A: builtin（type-param）| A | **A** | emit `call i8* @malloc(sizeof(T))` + 类型标记 + `%p = alloca (...)` ownership tracking | UltraCPP compiler |
| **`free(p)`** | A: builtin（type-param）| D（FFI，libc free）| **A** ⭐ NEW | emit `call void @free(i8* %p)` + 标记 p 为 freed（p 之后视为 dangling）| UltraCPP compiler |
| `move(p)` | A: builtin（type-param）| A | **A** | emit load + 标记 p 为 moved-out（p 之后视为 invalid）| UltraCPP compiler |
| `clone(s)` | A: builtin（type-param）| A | **A** | emit `alloc(T) + memcpy` + 标记新所有权 | UltraCPP compiler |
| **`mod(ref)`** | A: builtin（type-param）| B（intrinsic）| **A** ⭐ NEW | emit IR marker（borrow-check 进入可修改借权状态）| UltraCPP compiler |
| **`unmod(ref)`** | A: builtin（type-param）| B（intrinsic）| **A** ⭐ NEW | emit IR marker（borrow-check 退出可修改借权状态）| UltraCPP compiler |

> **关键变化**：
> 1. **`free` 从外部 FFI（`extern "C" malloc/free`）提升为 builtin**——理由：free 是 borrow-checker 必须追踪的状态变更点，不能让它透明地穿过 libc（否则 IR 无法标记 freed 状态）。
> 2. **`mod` / `unmod` 从 intrinsic（B 类）提升为 builtin（A 类）**——理由同 free：它们是 borrow-checker 状态入口/出口，编译器必须在 IR 中显式记录。

**最终 BUILTIN_SIGS[] 共 6 项**（取代 0.3.3 计划 A 的 7 项）。

### 5.2 编译器 intrinsic（不进 BUILTIN_SIGS[]，codegen 特殊处理）

| 函数 | 类别 | codegen 处理 | 说明 |
|---|---|---|---|
| `null` | B: intrinsic | emit `i8* null` 常量 | 编译期常量；不进 BUILTIN_SIGS |
| `is_null(p)` | B: intrinsic | emit `icmp eq i8* %p, null` | 不需要函数调用；codegen 直接翻译 |
| `sizeof(T)` | B: intrinsic | emit `i32 sizeof(T)` 编译期常量 | 类型算子，不需要函数调用 |
| `alignof(T)` | B: intrinsic | emit `i32 alignof(T)` 编译期常量 | 同上 |
| `mod(p)`（仅作为编译期决策时的版本）| B: intrinsic（变体）| emit 编译期常量 | 若 mod 仅用于编译决策可降级；但若作为运行时借权状态机则升级为 A 类 builtin（见 §5.1）|

> 原则：intrinsic = "不需要函数调用就能 emit IR"（编译期就决定了）。B 类与 A 类的边界是「是否需要 emit `call` 指令」。

### 5.3 不进 BUILTIN_SIGS[] 的项目（被替代或废弃）

| 旧项目 | 替代/废弃 | 备注 |
|---|---|---|
| `sizeof_impl()` 函数 | 改用 `sizeof(T)` 算子 | 之前是 call 函数，无 parser keyword |
| `alignof_impl()` 函数 | 改用 `alignof(T)` 算子 | 同上 |
| `clone_impl()` 函数 | 改用 `clone(s)` builtin | 重复 |
| `print*` (作为 builtin) | 改 UltraCPP stdlib (`lib/print.uc`) | stdlib 而不是 builtin |
| `strlen/strcpy/strcmp/memcpy/memmove/memset/abs_int` (作为 builtin 或 FFI) | 改 UltraCPP stdlib (`lib/string.uc` 等) | **UltraCPP 自己实现，不接 libc**（§3.1）|

### 6.3 跨平台统一命名原则

- **用户代码用 `sys::read(fd, buf, len)`**——所有平台相同。
- **实现按 `@ifdef(TARGET_OS_*)` 区分**——同一接口名在不同平台分发到不同实现。
- **目录组织**：
  ```
  lib/sys/
  ├── sys.uc          // sys:: namespace API 公共头
  ├── raw.uc          // sys::raw_syscall low-level 实现
  ├── linux_uc        // Linux-specific 实现（@ifdef 标记）
  ├── darwin_uc       // macOS-specific 实现
  ├── windows_uc      // Windows-specific 实现（Win32 syscalls）
  └── freebsd_uc      // FreeBSD-specific 实现
  ```

## 7. 预编译宏机制 (Preprocessor macros)

### 7.1 UltraCPP 宏语法（C 风格）

```c
@ifdef(TARGET_OS_LINUX)
    // Linux 实现
@end

@ifdef(TARGET_OS_DARWIN)
    // macOS 实现
@end

@if defined(TARGET_OS_LINUX) && defined(TARGET_ARCH_X86_64)
    // x86_64 Linux 特定代码
@end

@if !defined(TARGET_OS_LINUX)
    @error("lib/sys/raw.uc 仅支持 Linux，其他平台需单独实现")
@end
```

- **`@ifdef(MACRO)` / `@end`**：单条件（等效 C 的 `#ifdef MACRO` / `#endif`）。
- **`@if defined(MACRO) && defined(MACRO2)`**：复合条件（等效 C 的 `#if defined(MACRO) && defined(MACRO2)`）。
- **`@ifndef(MACRO)` / `@end`**：反向（等效 C 的 `#ifndef`）。
- **`@else` / `@elif`**：分支（等效 `#else` / `#elif`）。
- **`@define(NAME, VALUE)`**：宏定义。
- **`@error("msg")`**：编译期错误。

### 7.2 预定义宏

| 宏 | 值 | 用途 |
|---|---|---|
| `TARGET_OS_LINUX` | 1 | Linux 平台 |
| `TARGET_OS_DARWIN` | 1 | macOS 平台 |
| `TARGET_OS_WINDOWS` | 1 | Windows 平台 |
| `TARGET_OS_FREEBSD` | 1 | FreeBSD 平台 |
| `TARGET_ARCH_X86_64` | 1 | x86_64 架构 |
| `TARGET_ARCH_AARCH64` | 1 | ARM 64 架构 |
| `TARGET_ARCH_RISCV64` | 1 | RISC-V 64 架构 |
| `TARGET_ULTRA_VERSION` | "0.3.3" | UltraCPP 编译器版本 |
| `TARGET_ULTRA_FEATURES` | 位标志 | 启用的语言特性 |

### 7.3 vs Rust `#[cfg]`

| UltraCPP（C 风格）| Rust |
|---|---|
| `@ifdef(TARGET_OS_LINUX) ... @end` | `#[cfg(target_os = "linux")]` |
| `@if defined(TARGET_OS_LINUX)` | `#[cfg(all(target_os = "linux", ...))]` |
| `@if !defined(TARGET_OS_LINUX)` | `#[cfg(not(target_os = "linux"))]` |
| 文件级：`@ifdef` 包裹整个文件 | `#[cfg(...)] mod unix;`（mod Unix 中所有项被 cfg 限制）|
| `@define(NAME, VALUE)` | 没有等价（Rust 通过 `const`）|
| `@error("msg")` | `compile_error!("msg")` |

## 8. 内联汇编机制 (Inline assembly)

### 8.1 UltraCPP asm 语法（C / GCC 风格）

```c
fn raw_syscall(num: int, arg1: int) -> int {
    int result;
    asm {
        "syscall"
        : "=a"(result)               // 输出操作数
        : "0"(num), "D"(arg1)         // 输入操作数（0 = 与输出 0 复用）
        : "rcx", "r11", "cc", "memory"  // clobbers
    }
    return result;
}
```

格式（4 段）：

1. **指令模板**：`"syscall"`
2. **输出操作数**：`: "=a"(result)` —— `=` 表示只写
3. **输入操作数**：`: "0"(num), "D"(arg1)` —— `"0"` 表示与输出 0 同寄存器
4. **Clobbers**：`: "rcx", "r11", "cc", "memory"` —— 调用者保存 / 内存可能被改

### 8.2 约束字符（参考 GCC）

| 约束 | 含义 |
|---|---|
| `r` | 任意通用寄存器 |
| `a` | rax/eax（x86_64 syscall num） |
| `D` | rdi/edi（x86_64 第 1 参） |
| `S` | rsi/esi（x86_64 第 2 参） |
| `d` | rdx/edx（x86_64 第 3 参） |
| `c` | rcx/ecx（x86_64 第 4 参，syscall 后被 clobber） |
| `b` | rbx/ebx（x86_64 第 5 参） |
| `=r` | 输出寄存器（只写） |
| `+r` | 读写操作数 |
| `0`-`7` | 与第 N 个操作数复用同一寄存器 |
| `r0`-`r7` | ARM / RISC-V 寄存器编号 |
| `m` | 内存操作数 |
| `i` | 立即数 |
| `cc` | 条件码寄存器（flags） |
| `memory` | 内存可能被改（编译器需刷新寄存器缓存） |

### 8.3 vs Rust `asm!`

| UltraCPP（C 风格）| Rust `asm!` |
|---|---|
| `asm { "syscall" : "=a"(r) : "0"(n) : "cc" }` | `asm!("syscall", out("rax") r, in("rax") n, lateout("rcx") _, lateout("r11") _, options(preserves_flags))` |
| Clobber list 第四段 | `lateout(...)` / `options(...)` |
| `"0"` 复用前操作数 | 直接传同名变量 |
| `asm volatile { ... }` | `options(preserves_flags, nostack)` 等 |

UltraCPP 选 C 风格：与 `src-c/` 当前 C 实现无缝；LLVM 工具链直接理解；学习曲线友好。

## 9. 自举计划 (Bootstrap plan)

### 9.1 三阶段

```
┌──────────────────────────────────────────────────────────┐
│ Stage 0: src-c/ (C 实现的 uc compiler)                   │
│   - src-c/src/codegen.c, parser.c, ast.c, ...            │
│   - src-c/Makefile                                        │
│   - 输出: uc_compiler (binary, 主机平台)                  │
└──────────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────────┐
│ Stage 1: uc_compiler 编译 lib/*.uc                       │
│   - lib/print.uc        ← UltraCPP stdlib (UltraCPP 写)  │
│   - lib/string.uc       ← strlen/strcpy/strcmp            │
│   - lib/memory.uc       ← memcpy/memmove/memset           │
│   - lib/math.uc         ← abs 等                          │
│   - lib/sys.uc          ← sys:: namespace                 │
│   - lib/alloc.uc        ← builtin alloc 的 thin wrapper   │
│   - lib/sync.uc         ← mutex/atomic 包装               │
│   - 输出: libuc.a (UltraCPP runtime 静态库)               │
└──────────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────────┐
│ Stage 2: 自举（可选, 远期目标）                            │
│   - uc_compiler_v2（用 src-c 编译，链接 libuc.a）         │
│   - uc_compiler_v2 编译 lib/*.uc                          │
│   - uc_compiler_v2 编译自己（src-c 翻译为 .uc 源码）       │
│   - 输出: uc_compiler_v2 (binary)                         │
└──────────────────────────────────────────────────────────┘
```

### 9.2 lib/ 目录结构（规划）

```
lib/
├── print.uc              // uc_print(s), uc_print_num(n), uc_print_float(f)
├── string.uc             // uc_strlen, uc_strcpy, uc_strcmp, ...
├── memory.uc             // uc_memcpy, uc_memmove, uc_memset, ...
├── math.uc               // uc_abs
├── alloc.uc              // thin wrapper around builtin alloc (allocation counting, debug)
├── sync.uc               // uc_mutex, uc_atomic
├── sys/
│   ├── sys.uc            // high-level sys:: namespace API
│   ├── raw.uc            // low-level raw_syscall (asm 指令)
│   ├── linux_uc          // Linux-specific impl (@ifdef)
│   ├── darwin_uc         // macOS-specific impl
│   ├── windows_uc        // Windows-specific impl
│   └── ...
└── test/
    └── test_runtime.uc   // runtime 单元测试
```

### 9.3 与 0.3.x 阶段的关系

| 阶段 | runtime 状态 |
|---|---|
| 0.3.1-0.3.2 | C 实现的 `lib/uc_runtime.c`（bootstrap 临时）|
| 0.3.3 | spec + codegen 完成；runtime 仍 C 临时（bootstrap 必需）|
| 0.3.4-0.3.7 | 仍用 C 临时 runtime；`lib/uc_runtime.c` 提供 print / strlen / memcpy 等 |
| 0.4.0+ | **首次自举**——用 uc_compiler 编译 lib/*.uc 替换 C 临时 runtime |
| 1.0 | 完全自举（uc_compiler 用自己编译，移除 src-c/）|

> **关键原则**：在 0.3.x 阶段（0.3.1 → 0.3.7），`lib/uc_runtime.c`（C 实现）是**临时 bootstrap**——它存在是为了让 0.3.x 阶段能工作；到 0.4.0+ 阶段，它应该被 `lib/*.uc`（UltraCPP 实现）**逐文件替换**。在 1.0 时，整个 `src-c/` 目录被移除（除非作为保留的后端实现）。
