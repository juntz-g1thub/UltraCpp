## 2. 问题描述

### 2.1 当前 spec §4.6 缺失 lvalue / rvalue 概念

`docs/UltraCPP-v0.3.0-spec-zh-CN.md` §4.6(行 541 起)的 11 行表格只列了 `=`、`+=`、`-=`、`*=`、`/=`、`%=`、`&=`、`|=`、`^=`、`<<=`、`>>=`,每行只描述运算符含义,**没说 "LHS 必须是 lvalue" 这一基本约束**。

这是 C/C++ 教科书写明但 spec 当前缺失的核心语义。

### 2.2 §7.8 引用 "操作数必须是左值" 但 "左值" 没定义

`docs/UltraCPP-v0.3.0-spec-zh-CN.md` §7.8(行 1009 起)第 1 条创建规则写明"操作数必须是左值",但 spec 全文没有 "lvalue" 定义(只在 §4.9 `mod()` 操作数描述里半隐含地用了"左值"二字)。

概念散落两处,没有 anchor 章节。

### 2.3 §4.1 优先级表没列一元 `*` `&` `mod` `unmod`

`docs/UltraCPP-v0.3.0-spec-zh-CN.md` §4.1(行 477 起)只列了二元算术 / 关系 / 逻辑 / 赋值的优先级。一元 `*`(deref)、`&`(address-of)、`mod` / `unmod`、前缀 `++` / `--`、一元 `+` `-` `!` `~` 都没列。S2 借此机会补齐。

### 2.4 Bug C3 (m0_42 deref-assign) 根因

`test/programs/baseline/m0_42_*.uc` 包含 `*view = payload;` 这种 deref-assign。当前 codegen 的 `gen_expr` 在处理 `UC_EXPR_ASSIGN` 时,**LHS (`*view`) 一律走 rvalue 路径**(emit load),而不是 lvalue 路径(emit 地址)。结果 `*view` 先被 load 成临时值,store 回去时类型对不上,触发 codegen 类型错。

S2 fix: `gen_expr` 加 `int in_lvalue_ctx` 参数,`UC_EXPR_ASSIGN.target` 调用时传 1,走 lvalue 路径(emit gep 取地址)。

### 2.5 Bug C1 (UC_EXPR_CALL last_expr_type) 根因

`UC_EXPR_CALL` 调用表达式的类型传播需要"返回值是什么类型"的机制。当前 codegen 缺乏 `last_expr_type` 概念(不知道上一次 `gen_expr` 求出什么类型),S2 顺手引入 "每个表达式有 lvalue / rvalue 类别 + 一个具体类型" 这两个上下文信息。

## 3. 现有 spec 章节交互分析 (确认无冲突)

### 3.1 §4.9 `mod()` ↔ S2 lvalue

**§4.9 原文**(行 569 起):

> "操作数:`reference_expression` 必须是对引用类型 `T&` 的左值(即 `int&`、`Point&` 等)。"
> "mod(r) 必须先 mod(r);申请修改权,否则是编译期错误"

**S2 介入**:

- S2 §4.13 定义"lvalue"是哪些表达式(变量、deref、字段访问、索引、引用、pre-inc、赋值)
- `mod()` 接受 `T&` 参数 → `T&` 绑定 lvalue(由 §7.8 第 1 条已隐含)
- S2 让 mod 的"lvalue 要求"有了 spec 基础

**edge cases (S2 后行为)**:

| mod 调用 | S2 后状态 | 解释 |
|----------|----------|------|
| `mod(x)` | ✅ valid | x 是 lvalue(变量) |
| `mod(42)` | ❌ compile error | 42 是 rvalue(字面量) |
| `mod(x + 1)` | ❌ compile error | 算术结果是 rvalue |
| `mod(*p)` | ✅ valid | *p 是 lvalue(deref,见 §4.13.2 表) |
| `mod(&x)` | ❌ compile error | &x 结果是指针 rvalue |
| `mod(s.field)` | ✅ valid | field access 是 lvalue |
| `mod(arr[i])` | ✅ valid | index 是 lvalue |

**结论**: **S2 与 §4.9 无冲突**,S2 让 mod 的 "lvalue 要求" 有了 spec 基础,反而**强化** §4.9。

### 3.2 §4.10 `unmod()` ↔ S2 lvalue

**§4.10 原文**(行 610 起):

> "`unmod(ref_expr)` 显式释放修改权。**一般省略**——作用域结束或最后一次使用时编译器自动 unmod。"

**S2 介入**: 同 §4.9,`unmod()` 也要求 `ref_expr` 是 lvalue(因为 `T&` 绑 lvalue)。S2 让 `unmod()` 的 lvalue 要求有了基础。

**结论**: **S2 与 §4.10 无冲突**,互为补充。

### 3.3 §7.1 所有权 + 隐式 mod ↔ S2

**§7.1 原文**(行 856 起):

> "赋值 `p1 = p2` 的 `T*` 版本会**自动**生成 `mod(p1)`"
> "src 的所有权不变——它仍然 owns;除非显式 `move(src)` 才转"

**S2 介入**:

- 赋值 LHS = lvalue(由 S2 §4.13.2 定义)
- 隐式 mod(LHS)作用在 lvalue 上,well-defined
- S2 让"隐式 mod"的目标明确是 lvalue

**结论**: **S2 与 §7.1 无冲突**,S2 **强化** §7.1 的隐式 mod 语义。

### 3.4 §7.8 引用 `&T` ↔ S2 lvalue

**§7.8 原文**(行 1009 起):

> "1. 操作数必须是左值。"

**S2 介入**:

- S2 §4.13.2 定义"lvalue 哪些"
- §7.8 第 1 条改写为"操作数必须是 lvalue (见 §4.13.2)"
- 强化 §7.8 的精确度

**结论**: **S2 与 §7.8 完全一致**,S2 是 §7.8 的概念基础。

### 3.5 §3.8 `const T*` / `T* const` ↔ S2

**§3.8**(行 429 起)关注: 指针的可 rebind / 不可写 / owning heap 禁止

**S2** 关注: 表达式是 lvalue 还是 rvalue

两者是**不同维度**:
- const-correctness 是关于"通过指针能否写值"
- lvalue / rvalue 是关于"表达式能否作赋值左侧"

但 const-correctness 也依赖 lvalue:
- `const int* p = &x;` — 初始化 rvalue(指针值),p 本身 lvalue
- `*p = v` — *p 是 lvalue,但 const 禁止
- S2 让 const 规则的"LHS 是不是 lvalue"判断有了基础

**结论**: **S2 与 §3.8 无冲突**,互为补充。

### 3.6 综合: 5 个章节全无冲突

| spec 章节 | S2 关系 | 净效果 |
|-----------|---------|--------|
| §4.9 `mod()` | 强化(明确定义"lvalue") | mod 的输入要求有 spec 基础 |
| §4.10 `unmod()` | 强化(同 mod) | unmod 的输入要求有 spec 基础 |
| §7.1 隐式 mod | 强化(隐式 mod 目标明确) | 赋值隐式 mod 行为可追踪 |
| §7.8 引用 `&T` | 强化(引用的 lvalue 基础) | `&` 的"操作数"明确 |
| §3.8 `const T*` | 独立(不同维度) | 互不干扰 |

**总判断**: **S2 完全是 spec 概念强化,不破任何现有章节**。

## 4. Spec 修订内容 (diff 草稿)

### 4.1 新增 §4.13 (完整章节)

> 插入位置:`docs/UltraCPP-v0.3.0-spec-zh-CN.md` §4.12 之后,§5 之前。

```bnf
### 4.13 表达式分类:lvalue 与 rvalue *(0.3.1 新增)*

UltraCPP 中每个表达式属于以下两类之一:

#### 4.13.1 定义

**lvalue**(左值) — 标识一个对象,有持久身份:
- 有 identity(占据明确存储位置)
- 可作为赋值 `=` 左侧
- 可取地址 `&`
- 在 codegen 层:走 "lvalue 路径" — emit 取地址指令(`getelementptr`、`alloca` 引用等),**不**自动 load 值

**rvalue**(右值) — 表示一个临时值,无持久身份:
- 没有 identity(临时)
- **不**可作为赋值 `=` 左侧
- **不**可取地址
- 在 codegen 层:走 "rvalue 路径" — emit 求值指令(`load`、立即数等)

#### 4.13.2 哪些表达式是 lvalue

| 表达式 | 类别 | 原因 |
|--------|------|------|
| 变量名 `x` | lvalue | 标识对象 |
| 解引用 `*p` (p 是 `T*` 指针类型) | lvalue | 标识 p 指向的对象 |
| 字段访问 `s.field` | lvalue | 标识结构体中的成员 |
| 索引 `a[i]` | lvalue | 标识数组中的元素 |
| 引用 `&x` 的结果 `T&` | lvalue | 引用就是别名 |
| 前缀自增 `++x` | lvalue | 修改后的对象 |
| 赋值表达式 `x = v` | lvalue | (C++11 起,赋值结果是 LHS) |
| **函数调用 `f()` 的结果** | **rvalue** | 临时值 |
| 字面量 `42` | rvalue | 立即数 |
| 算术运算 `a + b` | rvalue | 计算结果 |
| 比较运算 `a < b` | rvalue | bool 值 |
| 后缀自增 `x++` | rvalue | 旧值,新值已写入 |
| 取地址 `&x` | **rvalue**(返回指针) | 虽操作 lvalue,结果是 rvalue |

#### 4.13.3 赋值上下文约束

`=` 左侧**必须**是 lvalue。**非 lvalue 作左侧是编译期错误**:

```c
42 = x;          // ❌ 字面量是 rvalue
x + 1 = 2;       // ❌ 算术表达式是 rvalue
f() = x;         // ❌ 函数调用结果是 rvalue
*x = v;          // ✅ *p 是 lvalue
s.field = v;     // ✅ 字段访问是 lvalue
a[i] = v;        // ✅ 索引是 lvalue
++x = 1;         // ✅ pre-inc 是 lvalue
x++ = 1;         // ❌ post-inc 是 rvalue(返回旧值)
```

#### 4.13.4 codegen 实现约束

对 lvalue 表达式,调用 `gen_expr` 在不同上下文有不同行为:

| 调用上下文 | lvalue 表达式 codegen 行为 |
|-----------|--------------------------|
| 赋值 LHS(`UC_EXPR_ASSIGN.target`) | 走 lvalue 路径:emit 取地址(`getelementptr` / `alloca` 引用) |
| 取地址操作数 `&x` | 走 lvalue 路径:emit 栈 / 全局地址 |
| 表达式内部 / 表达式语句 / 函数实参 | 走 rvalue 路径:emit `load` 或值复制 |

例:

```c
int x = 42;
int* p = &x;
*p = v;           // LHS: lvalue 路径 → emit gep
y = *p;           // RHS: rvalue 路径 → emit load
int z = *p + 1;   // RHS: rvalue 路径 → emit load + add
```

> **与 C/C++ 对比**:UltraCPP 的 lvalue / rvalue 二元分类与 C/C++ 一致。但 UltraCPP 不区分 C++11 引入的 "xvalue"(eXpiring value)、"prvalue"(pure rvalue)、"glvalue"(generalized lvalue) 三分法——UltraCPP 只分两类,简单清晰。
```
